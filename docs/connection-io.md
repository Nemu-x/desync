# Connection I/O contracts

Wrap an established connection before the first TLS write. Empty transformation options return the original connection. The wrapper owns transformed writes; do not concurrently bypass it by writing to the underlying connection.

## Buffered and partial writes

The wrapper assembles the first complete ClientHello across TLS records and `Write` calls. It can return an incomplete fragment's accepted length before those bytes reach the socket. This is acceptance into the wrapper, not delivery or acknowledgement. A later write completes and transmits the handshake. Only incomplete input needs an owned assembly buffer; a large coalesced tail is passed on without being copied into it.

The result of each `Write` counts logical input from that call. It excludes bytes accepted by previous buffered calls and TLS headers generated by record fragmentation. On ordinary transformed socket writes, partial progress is preserved even if a later piece or trailing write fails. A failure partway through a generated header consumes no additional input bytes.

Any error after transformed transmission starts is terminal for the connection: it is closed and later writes return the stored error. The wrapper never replays the application's stream. On failure of the Windows asynchronous fake backend, a trustworthy logical prefix count is unavailable; it conservatively returns zero with the terminal error. Zero in this case does **not** mean no bytes may have reached the peer and is not permission to replay traffic.

## Deadlines and closing

Set deadlines on the returned wrapper, rather than on the underlying socket. An already closed connection or expired write deadline rejects a new buffered write. An expired deadline detected before consuming new input can be cleared or extended, preserving previously accepted fragments.

`SplitDelay` is an explicitly configured pause between writes, not ACK synchronization or a guarantee of separate TCP segments. It defaults to zero. A negative delay is rejected. `Close`, `SetDeadline` and `SetWriteDeadline` changes interrupt/recalculate active split waits, including clearing or extending a deadline. Reads remain independent of the initial writer lock.

The context passed to `net.Dialer.DialContext` controls dialing, not the lifetime of the returned connection. Applications should use `tls.Conn.HandshakeContext`, deadlines or close the connection on application cancellation. No background discovery, retries or public service probes run inside `WrapConn`.

## Split wait

`Options.SplitWait` makes the wrapper observe the real socket before it writes each further `Split` piece. `SplitWaitSent` waits until every byte written so far was transmitted at least once; `SplitWaitAcked` until the peer acknowledged every byte. The observer is created before the first piece: a connection without a TCP `SyscallConn` returns `ErrSplitWaitRequiresTCP`, and a socket whose query fails returns `ErrSplitWaitUnsupported`, in both cases before any byte is sent. `Validate` rejects a mode the OS cannot observe, a wait without split positions, and timeouts outside 0..1 minute. There is no fallback to back-to-back writes or to a sleep.

The wait polls: 16 scheduler yields, then sleeps from 50 µs doubling to 1 ms. Each sleep is cut short by `Close`, by any `SetDeadline`/`SetWriteDeadline` call and by the write deadline itself. `SplitWaitTimeout` (default 2 s) bounds each wait and ends it with `ErrSplitWaitTimeout`. Every error during the wait is terminal for the connection, like other errors after transformed transmission started, and the partial-write count covers the pieces already written. The wait holds no native resources, goroutines or timers after it returns.

What each OS observes, on the connection's own socket:

- **Linux and Android**: `ioctl(SIOCOUTQ)` returns `write_seq - snd_una` (written, not yet acknowledged) and `ioctl(SIOCOUTQNSD)` returns `write_seq - snd_nxt` (written, never transmitted); see [tcp(7)](https://man7.org/linux/man-pages/man7/tcp.7.html). `SplitWaitAcked` waits for the first to be zero, `SplitWaitSent` for the second. The ioctls are the first choice: they are byte counts of the current queue on every kernel since 2.6.38. `ProbeConn` reports `Unacked`, `Unsent` and `InFlight`, and the mechanism the socket uses in `Ack.Mechanism`. Where `SIOCOUTQNSD` is denied, see [Android](#android-send-queue-observation).
- **macOS**: `getsockopt(SOL_SOCKET, SO_NWRITE)` returns `so_snd.sb_cc`. TCP keeps sent data in the send buffer until it is acknowledged (`sbdrop` in `tcp_input`), so zero means everything was acknowledged. The public `TCP_CONNECTION_INFO` (0x106) reports the same value as `tcpi_snd_sbbytes` ("bytes in send socket buffer, including in-flight data"); the structure with `snd_una`/`txunacked` (`TCP_INFO`) is private. Neither public interface separates unsent from in-flight bytes, so `SplitWaitSent` is unsupported there. Sources: xnu [`bsd/netinet/tcp.h`](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/netinet/tcp.h), [`tcp_usrreq.c`](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/netinet/tcp_usrreq.c) (`tcp_connection_fill_info`), [`uipc_socket.c`](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/uipc_socket.c) (`SO_NWRITE`).
- **Windows 10 1703 / Server 2016 and later**: [`SIO_TCP_INFO`](https://learn.microsoft.com/en-us/windows/win32/winsock/sio-tcp-info) version 0 returns [`TCP_INFO_v0`](https://learn.microsoft.com/en-us/windows/win32/api/mstcpip/ns-mstcpip-tcp_info_v0) without elevation: `BytesInFlight` ("sent bytes that are unacknowledged"), `BytesOut` ("total number of bytes sent") and `BytesRetrans`. There is no unsent-bytes value. The wrapper samples `BytesOut - BytesRetrans` before its first piece and waits until it grew by the bytes written (`SplitWaitSent`) and, for `SplitWaitAcked`, `BytesInFlight` is zero. This is reported as not reliable: on loopback `BytesOut` matched writes up to 16 KiB exactly, but a 100,000-byte write counted 100,040 and a 1 MiB write against a 32 KiB receive buffer counted 1,375,590, with `BytesRetrans` zero. An inflated counter can end a wait before every byte was transmitted. Bytes written to the socket before wrapping that were still unsent at the baseline would also be counted. Per-connection extended statistics with `ThruBytesAcked`/`SndUna` (`GetPerTcpConnectionEStats`) need collection to be enabled with administrator rights, so they are not used.

`PlatformCapabilities().Ack.Reliable` is true only for the first two. A consumer that needs synchronization, not a best effort, should require it.

### Android send-queue observation

Android confines apps with SELinux, and its policy filters socket ioctls by command (AOSP `system/sepolicy`, `private/app.te`: `allowxperm` for `unpriv_sock_ioctls` and `unpriv_tty_ioctls`, defined in `public/ioctl_macros`). `SIOCOUTQ` is the same number as `TIOCOUTQ` (0x5411) and is allowed; `SIOCOUTQNSD` (0x894b) is in `priv_sock_ioctls` and denied to untrusted apps since Android 8, Termux included, so it fails with `EACCES`. The `shell` domain of `adb shell` is denied it as well.

When `SIOCOUTQNSD` fails with `EACCES` or `EPERM` (on Android, or on Linux under a policy that denies it), the observer reads `getsockopt(IPPROTO_TCP, TCP_INFO)` and takes `tcpi_notsent_bytes`, which `tcp_get_info` fills with `write_seq - snd_nxt`, the value `SIOCOUTQNSD` returns. `struct tcp_info` (`include/uapi/linux/tcp.h`) has eight `__u8` and 24 `__u32` fields before its first `__u64` at offset 104, which is 8-byte aligned, so i386 (which aligns `__u64` to 4) and the 64-bit ABIs share one layout: `tcpi_notsent_bytes` is the `__u32` at offset 144, added in Linux 4.6. The wrapper requests 148 bytes; the kernel copies `min(optlen, sizeof(struct tcp_info))` and returns that length, so an older kernel answers with fewer bytes (144 on 4.2–4.5) and the socket has no unsent count. On linux/386 the call goes through `socketcall`, as the other byte-sized socket options do. A Linux test reads both values on a socket whose peer window is full: they are equal (983,094 bytes) and both zero once the peer read everything.

The decision is made once per connection, when its first piece is prepared, and the denied ioctl is not retried. Then:

- with `tcpi_notsent_bytes`: `SplitWaitSent`, `Disorder` and `Fake` behave as with `SIOCOUTQNSD` (`Ack.Mechanism` `SIOCOUTQ/TCP_INFO`, still `Reliable`, `Disorder.Mechanism` `TCP_INFO`);
- without it: `SplitWaitAcked` and `OOB` still work; `SplitWaitSent`, `Disorder` and `Fake` fail the first `Write` with `ErrSplitWaitUnsupported`, `ErrDisorderUnsupported` or `ErrFakeUnsupported`, wrapping the `EACCES` and the missing field, before any byte reaches the socket and before any hop limit changes. Nothing is replaced by a delay or another method.

Because this depends on the kernel, `PlatformCapabilities()` on Android does not claim those three: `Ack.Sent`, `FakeTCP` and `Disorder.Supported` are false, and `Conditional` (and `Unsupported`) name them with the reason. `Validate` still accepts them. `ProbeCapabilities(conn)` returns the capabilities of a live socket with `Conditional` resolved; the restriction belongs to the process's SELinux domain and the kernel, so a loopback connection answers for every connection of the process (`desync-probe` does that). `ProbeConn(conn).SentErr` explains a socket without the unsent count.

Tests reproduce the denial on Linux by replacing the ioctl/getsockopt layer: `SIOCOUTQNSD` returns `EACCES`, and `TCP_INFO` is optionally cut to 144 bytes. With the field, the fake, disorder and `SplitWaitSent` deliver the exact stream, including through the low-hop drop filter (`TestLinuxLowHopDropRetransmitsOriginal`, `siocoutqnsd-denied/...`); without it, each fails before the server receives a byte. On an Android 16 emulator (x86_64 `google_apis` userdebug image, kernel 6.6, enforcing), the android/amd64 test binary ran in the `shell` domain and, from a debuggable app through `run-as`, in the `runas_app` app domain: the kernel logged `avc: denied { ioctl } ... ioctlcmd=0x894b` once per connection, the sockets used `SIOCOUTQ/TCP_INFO`, and the fake, disorder, `SplitWaitSent` and low-hop drop tests passed. A physical device, a kernel before 4.6 and the `untrusted_app` domain of an installed app started by the system were not tested.

## Framing and bounds

Record lengths and the 24-bit handshake length are parsed independently. SNI can cross input record headers; its logical bytes are read without concatenating the handshake into a second body buffer. Existing record boundaries and versions are preserved, with new valid record headers inserted only at configured interior cuts. Bytes after the ClientHello in its final record and all subsequent input are retained.

`ParseHello` now requires the complete first handshake and returns `ErrIncompleteClientHello` when only its first fragment is available. `Hello.RecordLen` retains its original meaning: the length of the first input record. `Hello.SNIOffset` is the start in the original wire input; the hostname may cross headers, so use `Hello.SNI` rather than assuming its wire bytes are contiguous. This deliberately replaces the old false success with missing SNI for incomplete input.

Absolute positions count original wire bytes. SNI-relative positions count logical handshake bytes and skip existing headers. Missing-SNI/out-of-range cuts remain ignored. TLS record cuts cannot create an empty record or split an existing header. Optional `Options.Random` ranges add cuts drawn once per connection among logical handshake byte boundaries, under the same framing rules; a nil policy keeps the path deterministic. There is no automatic strategy substitution in this path.

```go
opts := desync.Options{
    TLSRec: []desync.Pos{{Offset: 1, FromSNI: true}},
    ClientHello: &desync.ClientHelloOptions{
        MaxSize:    64 << 10,        // Includes the four-byte handshake header.
        MaxRecords: 256,
        Timeout:    5 * time.Second, // Incomplete input assembly only.
    },
}
```

Nil options and zero fields use these defaults. Maximum configurable bounds are 1 MiB, 4096 records and one minute. The wire-buffer bound additionally allows one final record payload and the bounded input headers; it excludes the caller's subsequent tail. Input growth is geometric with bounded capacity, instead of copying the entire accumulated buffer for every fragment. The options are cloned at wrap time.

`ErrClientHelloTooLarge` and `ErrTooManyClientHelloRecords` terminate the connection before transforming the oversized handshake. Malformed framing/vectors and other traffic pass through unchanged. `ErrClientHelloTimeout` closes the connection, wakes pending reads/writes, implements `net.Error` with `Timeout() == true`, and matches `os.ErrDeadlineExceeded`. The absolute timer starts with the first incomplete accepted fragment and is not extended by more input. Completion or `Close` cancels it; normal socket transmission and the destination's TLS response are not timed by this assembly clock. Clearing a write deadline does not disable the assembly bound.

The implementation follows [TLS record framing, RFC 8446 section 5.1](https://datatracker.ietf.org/doc/html/rfc8446#section-5.1). Local TLS/regression tests validate byte-stream correctness; they do not establish provider DPI effectiveness.

## Disorder and out-of-band byte

`Options.Disorder` and `Options.OOB` change how the first TCP piece of a split ClientHello is sent; every later piece is an ordinary write. They need split positions (`Split` or `Random.Split`); when none resolves for a ClientHello, it is written in one piece, as with `Split` alone. Both are prepared before the first piece: a connection without a TCP `SyscallConn` returns `ErrSocketMethodRequiresTCP` before any byte is sent, and an OS without the method fails `Validate` with `ErrDisorderUnsupported` / `ErrOOBUnsupported`. Both combine with `Fake` on a later piece (see [fake with split pieces](#fake-with-split-pieces)); `Disorder` rejects `SplitWaitAcked`, because the dropped piece is acknowledged only after its retransmission, so the wait would undo the reordering. `SplitWaitSent` and `SplitDelay` apply between the later pieces as usual.

Disorder (ByeDPI `--disorder`): the hop limit of the connected peer's family is set to 1, the first piece is written, the hop limit is restored, then the remaining pieces follow. The piece expires at the first router; the server receives the later pieces first, acknowledges what it can (with SACK), and the client's TCP retransmits the first piece with the restored limit. The kernel stamps the hop limit when it builds a segment, not when `write` returns, so the restore must wait for the transmission:

- **Linux and Android**: the wrapper waits until `SIOCOUTQNSD` (or, where it is denied, `tcpi_notsent_bytes`) is zero, so the piece left the send queue at hop limit 1. A socket that reports neither fails before the piece is written.
- **Windows**: it waits until `SIO_TCP_INFO` counts the piece as sent (`BytesOut - BytesRetrans`), which is exact for writes of this size but counter-based (`Reliable: false`).
- **macOS**: no public interface reports unsent bytes. The wrapper writes the piece only once `SO_NWRITE` is zero, so the send buffer is empty; xnu's `tcp_usr_send` then calls `tcp_output`, which builds the segment within the send call, as nothing else is queued, the window is open and Nagle is off. The restore follows the send. This is inferred, not observed, and `PlatformCapabilities().Disorder.Observed` is false.

The wait uses the split-wait poll, bounded by `SplitWaitTimeout` (`ErrSplitWaitTimeout`), the write deadline and `Close`. The hop limit is restored on every path, including a failed write and an interrupted wait; a failed restore is reported and, like every error after transformed transmission started, closes the connection. A connection whose write failed after the change is never left with hop limit 1.

Out-of-band byte (ByeDPI `--oob`, with Disorder `--disoob`): the first piece and one more byte (`OOBOptions.Byte`, default `'a'`) are sent in one `send(MSG_OOB)` call (`WSASend` with `MSG_OOB` on Windows), which marks that last byte as urgent data. The byte takes one sequence number on the wire, so an inspecting device that ignores the urgent pointer reads one extra byte after the first piece. A receiver without `SO_OOBINLINE` (the default everywhere) removes the urgent byte from the stream and keeps it for `recv(MSG_OOB)`, so the application reads the original bytes. This is verified on Windows and Linux loopback with the server reading the stream byte-identically, and with `SO_OOBINLINE` set the server reads the urgent byte exactly at the split point. Two conditions break it: a server application that enables `SO_OOBINLINE`, and a middlebox that clears the URG flag (some firewalls do); both put the byte into the stream and fail the handshake. With Disorder the urgent byte is part of the low-hop segment and of its retransmission, which carries the URG flag again while the urgent pointer is ahead of the acknowledged data.

## Linux native fake

The Linux and Android fake follows ByeDPI's `send_fake`: the fake prefix is copied into a shared anonymous mapping, `vmsplice` puts references to its pages into a pipe, and `splice` moves them into the socket's send queue at the low hop limit. The queued segment refers to the page, not to a copy. Once `SIOCOUTQNSD` (or `tcpi_notsent_bytes`, see [Android](#android-send-queue-observation)) reports the prefix transmitted, the page is overwritten with the original bytes, and only then is the hop limit restored and the normal tail written. A retransmission reads the page and carries the original. The mapping is `MAP_SHARED`, so a `fork` cannot make it copy-on-write and leave the kernel's reference on a page that still holds the fake bytes.

The page is rewritten before the hop limit is restored on every path, including errors and timeouts, so no normal-hop transmission can carry the fake. The splice runs non-blocking inside `RawConn.Control`; waiting for socket space and for the transmission polls under `Fake.Timeout` (default 3 s), the write deadline and `Close`. Afterwards the pipe is closed and the mapping unmapped; the kernel keeps its own page references, whose content is then the original. At most 64 operations hold resources at once (`ErrFakeBusy`). Prefixes larger than a pipe are moved in 64 KiB rounds.

The kernel splices without copying only when the route's device supports scatter-gather (`NETIF_F_SG`); loopback, Ethernet, Wi-Fi, tun and WireGuard devices do. On a device without it the kernel copies the spliced data, a retransmission repeats the fake, and the server's TLS handshake fails rather than succeeding with altered bytes.

A loopback test verifies the property directly: a classic BPF socket filter on the server's socket drops every segment with a TTL or hop limit below 8 before TCP processing, the client sends a fake prefix of different bytes with TTL 3, and the server still reads the exact original stream after the client's retransmission (`tcpi_total_retrans` 1). Disabling the page rewrite makes the server read the fake bytes. The same filter verifies disorder and disoob, the fake combined with split pieces, disorder, OOB, `SplitWaitSent` and random cuts, and decoy ClientHellos with another server name (`TestLinuxLowHopDropRetransmitsOriginal`).

## Fake with split pieces

With `Split` or `Random.Split` positions the fake prefix end (`Fake.Prefix`, measured after record fragmentation) becomes one more cut, and the piece that ends there, starting at the previous cut or at 0, is sent as the fake; this is ByeDPI's `--fake` as one part among `--split`, `--disorder` and `--oob` parts. Every other piece is an ordinary write; `Disorder` and `OOB` still act on the first piece, and `SplitDelay` and `SplitWaitSent` apply between all pieces. `SplitWaitAcked` is rejected: the low-hop piece is acknowledged only after its retransmission. When, for a given ClientHello, no split cut lies before the fake end while `Disorder` or `OOB` is set, the first piece would need two methods; the write then fails with `ErrFakeFirstPiece` before anything is sent (it is terminal, like other first-write errors). When no split position resolves, the hello is sent as with `Fake` alone.

Every guarantee of the single fake holds for the piece: the hop limit is restored on every path, a retransmission carries the original bytes, native waits are bounded by `Fake.Timeout`, the write deadline and `Close`, and any error after the first transformed send is terminal.

- **Linux and Android**: before lowering the hop limit for a fake piece that does not start the stream, the wrapper polls until `SIOCOUTQNSD` (or `tcpi_notsent_bytes`) is zero (bounded like the fake itself), so no byte of an earlier piece is built into a segment with the low hop limit; ByeDPI waits the same way (`sock_has_notsent`) between parts. Then the piece is spliced as before; the pieces after it are written once the page holds the original bytes and the hop limit is restored.
- **Windows**: the piece goes out through `TransmitFile` as before; the later pieces (with their waits and delays) are written right after the request is submitted and before its completion is awaited, as the single tail is. No wait precedes the piece: as in ByeDPI, the TTL is set around the `TransmitFile` request. The process-wide two-transmission slot is held while those later pieces are written, so a long `SplitDelay` after a fake piece delays other connections' fakes.

Write accounting: once the fake piece has started, a failure reports only the bytes of the pieces before it (generated record headers excluded), never more than what reached the socket; zero is still not permission to replay.

The decoy (`Payload`, the template, or a decoy ClientHello) starts at `Fake.Offset` and is zero-padded or truncated to the piece length. A fake piece in the middle of the stream therefore carries the beginning of the decoy unless `Offset` moves it (ByeDPI `--fake-offset`).

## Decoy ClientHello

`Fake.SNI`, `Fake.FromOriginal` and `Fake.Randomize` (ByeDPI `--fake-sni`, `--fake-tls-mod orig`, `--fake-tls-mod rand`) make the decoy a ClientHello built per connection. The base (the template, a custom `Payload`, or with `FromOriginal` the connection's own hello, reassembled across its input records) is decoded into its fields and extensions, changed, and encoded again with every length (record, handshake, extensions, server name list) recomputed, in records of at most 16 KiB. `SNI` replaces the server_name extension, or prepends one when the base has none; one name is drawn per connection from `crypto/rand`, with `*`, `?` and `#` replaced by a random letter or digit, letter, or digit. A padding extension absorbs the length change where it can. `Randomize` replaces the random, the session ID and every key share value, keeping their lengths. ByeDPI instead resizes the hello in place to keep its size; here only the template keeps its size, through its padding extension.

`Validate` checks names as DNS host names (letters, digits and hyphens, labels of 1 to 63 bytes, at most 253 bytes, no IP literals; at most 64 names), that a custom `Payload` decodes as a ClientHello when it is to be modified, that `FromOriginal` has `SNI` or `Randomize` and no `Payload`, and that `Offset` is between 0 and 65535. `Options.Key()` lists the names, `orig`, `rand` and `offset` only when set.

## macOS TCP fake

Not implemented, and reported in `PlatformCapabilities().Unsupported["fake-tcp"]`. The fake needs a first transmission whose bytes differ from what the socket later retransmits. Linux gets that from splice, which queues page references; Windows from `TransmitFile`, which reads the file cache at transmission time. xnu has no `splice` or `vmsplice`, and its `sendfile` allocates mbufs (`alloc_sendpkt`) and reads the file into them (`fo_read`) before `pru_send` appends them to the socket buffer (`bsd/kern/uipc_syscalls.c`, `sendfile`): the socket buffer holds a copy, so changing the file afterwards never reaches a retransmission, and the server would receive the fake bytes. There is no `MSG_ZEROCOPY` either. Writing the fake and later the original through ordinary writes would add bytes to the stream instead of replacing them.

## Automatic TTL

`FakeOptions.AutoTTL` needs the TTL (IPv6: hop limit) with which the server's packets reach the client, read from the client's own TCP socket before the ClientHello is sent, without raw sockets or privileges. The only packet received by then is the SYN-ACK.

| OS | Received TTL on a TCP socket | Result |
| --- | --- | --- |
| Linux, Android, IPv6 | With `IPV6_RECVHOPLIMIT` set, `tcp_v6_do_rcv` clones each segment and at `ipv6_pktoptions` stores the hop limit of the last in-order one (the SYN-ACK, which completes `connect`) in `np->mcast_hops`; `getsockopt(IPV6_2292PKTOPTIONS)` returns it as an `IPV6_HOPLIMIT` control message (`net/ipv6/tcp_ipv6.c`, `net/ipv6/ipv6_sockglue.c`) | supported |
| Linux, Android, IPv4 (and IPv4-mapped) | `tcp_v4_do_rcv` records nothing. `IP_PKTOPTIONS` reports `inet->mc_ttl`, which only `tcp_v4_syn_recv_sock` (an accepted socket) sets from a received packet; `IP_RECVTTL` control data is delivered to datagram sockets only (`net/ipv4/ip_sockglue.c`, `net/ipv4/tcp_ipv4.c`). A test reads `1` where the server sent 120 | unsupported |
| macOS, iOS | `tcp_input` never calls `ip_savecontrol`/`ip6_savecontrol`, and `ip6_ctloutput` answers `IPV6_2292PKTOPTIONS` with empty data (xnu `bsd/netinet/tcp_input.c`, `bsd/netinet6/ip6_output.c`) | unsupported |
| Windows | Received-TTL control data exists only for `WSARecvMsg`, which, like `IP_RECVTTL`/`IPV6_RECVHOPLIMIT`, is limited to `SOCK_DGRAM`/`SOCK_RAW`; `TCP_INFO_v0/v1` (`SIO_TCP_INFO`) has no TTL field | unsupported |

The option must be enabled before `connect` (`ControlAutoTTL` as `net.Dialer.Control`); otherwise the SYN-ACK is not recorded, nothing else arrives before the ClientHello, and `ObserveHops` reports `ErrAutoTTLUnobserved`. An unrecorded value reads as `IPV6_DEFAULT_MCASTHOPS` (1), which no estimate accepts. While the option is on, the kernel clones every received in-order segment, so the wrapper turns it off once it read the value. The value follows later in-order segments too: a test changes the server's hop limit after the handshake and reads the new one. A 32-bit process on a 64-bit kernel receives 64-bit control message headers here (`do_ipv6_getsockopt` does not set `MSG_CMSG_COMPAT`), so both layouts are parsed; linux/386 is tested on an amd64 kernel.

`EstimateHops` follows zapret's `hop_count_guess`: a received TTL of 33..64 started at 64, 97..128 at 128 and 224..255 at 255 (paths shorter than 32 hops); anything else is not guessed. `AutoTTL.TTL` follows `autottl_eval` with a negative delta: `hops - Delta` clamped to `Min..Max`, rejected unless it stays below the hop count. A packet sent with TTL `t` is dropped by the `t`-th router, so `hops - 1` still expires before the server; the margin absorbs a return path one hop shorter than the forward path. The estimate is wrong when the path is asymmetric, when the server (or a load balancer or CDN edge in front of it) starts at a non-standard TTL, or when an on-path device answers the handshake itself.

ByeDPI has no automatic TTL: it has `--ttl` (default 8) and `--auto` triggers that switch to another fixed group. zapret's `nfqws` reads the TTL of the first incoming packet through NFQUEUE, which needs root, and therefore also covers IPv4. Unprivileged alternatives that were not implemented: an ICMP echo (`IcmpSendEcho` on Windows; `SOCK_DGRAM`/`IPPROTO_ICMP` ping sockets on macOS, and on Linux where `net.ipv4.ping_group_range` allows them) reports the reply's TTL, but measures a different protocol that hosts and CDNs often filter or answer from elsewhere; a UDP probe needs a server that answers UDP; a traceroute through `IP_RECVERR` depends on ICMP time-exceeded replies from routers. Where nothing can be observed, `FakeTTLCandidates`/`UDPTTLCandidates` expand a TTL range into option sets with stable keys for discovery to probe.

## UDP burst and ICMP errors

The low-TTL datagrams can draw ICMP time-exceeded replies from the router where they expire. They must not fail the owned socket's `ReadFrom`:

- **Windows**: `SIO_UDP_NETRESET` is disabled on the socket.
- **Linux and Android**: an unconnected UDP socket is told about ICMP errors only with `IP_RECVERR` / `IPV6_RECVERR` (`__udp4_lib_err`, `__udp6_lib_err`); without it a soft error such as time exceeded is dropped, and a hard error is reported only on a connected socket. Both options are off by default; if the caller enabled them, `WrapPacketConn` turns them off. A loopback test shows a port-unreachable reply failing `ReadFrom` with `ECONNREFUSED` when `IP_RECVERR` is on, and not after wrapping.
- **macOS**: `udp_ctlinput` notifies only a socket whose foreign address and port match exactly, so an unconnected socket never sees the replies.

On a macOS dual-stack socket, `IPV6_UNICAST_HOPS` also sets the TTL of IPv4-mapped traffic, and `IPPROTO_IP` options are rejected. A default hop limit (-1) is therefore restored as its explicit value, and only when the IPv4 and IPv6 defaults (`net.inet.ip.ttl`, `net.inet6.ip6.hlim`) are equal; otherwise the burst fails with an error instead of changing the socket.

## QUIC Initial decoy

`UDPOptions.Template = UDPTemplateQUICInitial` replaces the 64 zero bytes with a QUIC version 1 client Initial packet generated per burst (every datagram of one burst is the same packet): a long header with a random 8-byte destination and source connection ID, no token, a 4-byte packet number 0, one CRYPTO frame at offset 0 with a ClientHello and PADDING frames to a 1200-byte datagram (RFC 9000 section 14.1). The ClientHello is the TCP template with `UDPOptions.SNI` (default `www.wikipedia.org`), fresh random values, no session ID and no padding extension, ALPN `h3`, and QUIC transport parameters carrying `initial_source_connection_id` and `max_idle_timeout`. The packet is protected like a real client's: AES-128-GCM with the client Initial key and IV derived from the destination connection ID with the version 1 salt, and AES header protection (RFC 9001 sections 5.2 to 5.4; HKDF is implemented with `crypto/hmac` because `crypto/hkdf` needs Go 1.24, and the derivation is tested against appendix A.1). Any observer can derive these keys, which is the point: a device that reads Initials sees the decoy name. `QUICInitialPayload(sni)` returns one such packet for a fixed `Payload`. ByeDPI v0.17.3 has no QUIC template; its `--udp-fake` sends the 64 zero bytes.

`UDPOptions.QUICOnly` applies the burst only to a datagram that looks like a client Initial: long header with the fixed bit, version 1 or a draft (`0xff0000xx`) with packet type 0, or version 2 with type 1, a destination connection ID of at most 20 bytes, and at least 1200 bytes. Other datagrams pass untouched and do not count towards `Packets` for the peer, so a DNS query before the QUIC handshake does not use up the burst. Hop-limit handling, ordering, source port and counters are unchanged.

## Windows native fake socket options

The TCP fake backend selects the TTL/hop-limit option for its connected peer's address family and restores that same option. It does not try to set IPv4 TTL on an IPv6-only connection merely because reading that option succeeded. This also keeps option selection explicit for IPv4-mapped peers. Native overlapped resource lifetime, cancellation and transmit-slot limits remain in place. Socket options are read through `syscall.Getsockopt` (ws2_32 `getsockopt`), because `syscall.GetsockoptInt` returns `EWINDOWS` on Windows before Go 1.21; the module's minimum Go 1.20 is tested on Windows in CI. See [IPv4 socket options](https://learn.microsoft.com/en-us/windows/win32/winsock/ipproto-ip-socket-options) and [IPv6 socket options](https://learn.microsoft.com/en-us/windows/win32/winsock/ipproto-ipv6-socket-options).
